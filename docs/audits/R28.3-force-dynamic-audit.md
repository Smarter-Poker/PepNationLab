# R28.3 — Audit Of `dynamic = 'force-dynamic'`

**Date:** 2026-06-02
**Scope:** Every `route.ts` and `page.tsx` in `app/` that opts out of static optimization with `export const dynamic = 'force-dynamic'`.
**Total hits:** 236 files.

## Why almost no conversions

The site is fully authenticated. There is no public unauthenticated content surface other than the legal/onboarding pages (`/login`, `/become-agent`, `/about`, `/terms`, `/privacy`, `/compliance`, `/disclaimer`) — none of which use `force-dynamic` today. Every other route legitimately reads at least one of: cookies, request body, `auth.uid()`-scoped data, or per-request idempotency keys.

Bulk-converting these to ISR would (a) break auth-gated routes by serving the wrong user's cached data, (b) break cron routes by short-circuiting per-execution side effects, (c) break webhook/idempotent POSTs by collapsing distinct requests, or (d) break analytics endpoints that record per-request facts.

## Specific findings

### `/api/health` — KEEP

```ts
export const dynamic = 'force-dynamic';
export async function GET() {
  return Response.json({ status: 'ok', service: 'pepnationlab', ts: new Date().toISOString() });
}
```

Looks like a candidate for static, but the point of a liveness probe is to confirm the runtime is hot. Caching defeats the purpose — an uptime monitor wants the *current* timestamp from the lambda, not a stale one served from the edge. `force-dynamic` is intentional and stays.

### `/api/health/crons` — KEEP

Admin-gated and reads `cron_runs`. Dynamic by necessity.

### `/account/help` (R28.2)

Already addressed: dropped redundant `force-dynamic` (cookies already force dynamic), parallelised the auth + role fetch via `Promise.all`. See commit `f998edde`.

### Public-facing dynamic pages that *could* benefit from ISR

These pages are not in this audit because they don't have `force-dynamic` — they already render via Next's automatic optimization based on whether they touch cookies. Pages worth verifying are correctly cached:

- `/login`, `/forgot-password` — should be ISR'd or static
- `/become-agent` — public form, should be ISR'd
- `/about`, `/terms`, `/privacy`, `/compliance`, `/disclaimer` — static legal content, must be ISR'd
- `/[slug]` (public storefronts) — currently dynamic, could be ISR with revalidate-on-tag when agent updates storefront

The above are NOT in scope for this audit (they don't use `force-dynamic`), but they're worth a follow-up perf pass to confirm Next.js is statically rendering them where possible.

## Recommendation

No bulk action is needed on the 236 `force-dynamic` files. They are correctly opting out of static optimization. The real perf wins are upstream: making sure the legal/onboarding pages above (which are NOT in this audit) are actually being statically rendered by Next.js as intended. That's a separate workstream.

## Process

To verify the cached behaviour of any individual route, the pattern is:

1. Hit it twice with `curl -sI -H 'Cache-Control: no-cache' <url>` and check `x-vercel-cache` header.
2. `MISS` followed by `HIT` = ISR working.
3. `BYPASS` or always `MISS` = correctly opted out for that route.

Routes serving per-user data should always show `BYPASS` or `MISS` — never `HIT`.
